### 🔴 The trap, and why a Serial proof is NOT enough here

The 8 arrays are DualViews whose raw host pointers were written in place by the host producer,
invisibly to the DualView. So **`fesom_bulk.cpp:520` and `fesom_ice.cpp:647` call
`modify_host(); sync_device()` on all 8 UNCONDITIONALLY, every step.** With a device producer those
rails **deep-copy the stale host mirror over the fresh device data.**

**On Serial the host and device views are the SAME MEMORY, so the rail is a no-op and the
FORCE_SERIAL byte proof passes whether or not you got this right.** The **CUDA fidelity gate is the
only gate that can see it.** Both CUDA gates passed (26249151 worst 9.9e-03; 26249152 worst 4.5e-03 —
the all-knobs run scoring *lower* than FORCEDEV-alone shows these are run-to-run atomics noise at the
floor, not a systematic D.1 effect).

**Three surviving host readers, each given a `sync_host()`:**
1. `fesom_cal_shortwave_rad` (`fesom_bulk.cpp`) — reads `jra->shortwave` **every step, in
   production**. ⚠️ **`SWSKIP` does NOT skip it** (it drops only the dead `sw_3d` half; the
   `heat_flux += swsurf` accumulation always runs). Costs one nod2D D2H ≈ 0.2 ms/step.
2. the host `fesom_bulk_compute` — **not verify-only**: `fesom_main.cpp:905` runs it once at init.
3. the host `fesom_ice_thermodynamics` twin — verify-only (`FESOM_KK_VERIFY=icethermo`).

**A fourth trap, found reviewing my own diff (not in any map):** `fesom_halo_fieldN` is guarded on
`partit`, and *it* is what sets `modify_device()`. On a single-rank run the halo call is skipped, so

every later `sync_host()` a silent no-op returning stale values. **The producer now calls

## 5. A.2 (hostprof) — how the forcing was found, and how the profiler lied (L82)

The host timer, not the sampler, is what settled it: **`force:jra55_read` = 75.2 ms/step at 1.0
calls/step** (+ `force:bulk_compute` 21.9 = the 97.1 ms forcing phase).

**The sampler blamed `getcoeffld` (38.3 ms/step). That function's body runs ZERO times in a 25-step
run** — it refreshes only when `rdate` leaves the 3-hourly JRA interval (1 step in 60 at dt180), and
the year-start prefetch covers step 1. (Verified by transcribing the C control flow to Python and
running it against the real `uas.1958.nc` axis: refreshes at steps 61/121/181.) It is `static`→inlined,
and `--backtrace=dwarf` **expands DWARF inline frames**, so the *caller's* per-node loop is reported
under the *inlined callee's* name.

**Rules (L82):** a sampler localises to a REGION and only *claims* to name a function — treat the name
as a hypothesis for anything `static`/inlined. **Before believing a per-step cost, ask how many times
the thing is CALLED per step.** Control flow beats any profile. Bracket the suspect with a **host
timer** (`FPROF`): a timer around a call cannot misattribute *which call* it timed.

**Also (L83):** a gate that never reads the lever's output is not evidence. The `io_acc_u/v`
accumulators write ONLY to `*.monthly.nc` while `diff_snap.py` globbed only `snap_*.nc` — the
FORCE_SERIAL proof would have run those kernels and **compared nothing they wrote**, and passed.
`diff_snap.py` now takes **`--pattern`** (default unchanged). **Name the file each lever's output lands
in, and check the gate opens it.**

**And this session's own version of it:** *size a lever by the work it REMOVES, not by the whole
function it lives in.* ROTCACHE was sized as `sincos` (23.5) **+ `g2r` self (13.8)** = 37 ms. Only the
`sincos` is removable — the matrix arithmetic in `g2r` survives, it just reads trig from a table.
Correct pool ≈ 23.5 − 4 (new table loads) ≈ **20 ms**; measured **19.7**. *Closes exactly.* Likewise
`FLAT` recovered 53% of its pool because `uv`/`uvnode` are **stride-2 interleaved** → even a perfectly
flat access is ~50% sector-efficient by construction (the packA handoff predicted this as trap #3).
