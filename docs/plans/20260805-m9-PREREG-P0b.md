# M9 P0b pre-registration — the FUSED build of cell ② (decision D1)

**Committed before the first timing leg.** Session 3, 2026-08-05.
Precedent: `20260804-m9-PREREG.md` and `20260805-m9-PREREG-P1.md`. The value of doing this twice
already showed up once (H1 was falsified and reported as such because the fallback was written
down in advance), so the predictions below are written before any number exists to argue about.

---

## 1. What is being measured, and why it is the last piece of H3

Cell ② (classic form, exact wide halo) carries element stress, so its window ship needs two
segments: nodes `(u_aux, v_aux)` and the ghost-element σ. Cell ④ (divergence form) carries only
node quantities, so it needs one. RESULTS §9.7 measured ④ beating ② on GPU everywhere — by
1.9–2.8 pp at K=8 and up to 7.1 pp at K=2 — and read that as H3's **byte** term (② ships `8·Ng`
doubles against ④'s `4·Ng`).

**That reading is not established, because ② carries two handicaps at once**: twice the bytes
*and* twice the messages. The fused build removes the second one by construction:

| | bytes/window | messages/partner/window |
|---|---|---|
| ② unfused | 8·Ng | **2** |
| **② fused (new)** | 8·Ng | **1** |
| ④ | 4·Ng | 1 |

So the campaign now has an exact two-term decomposition at matched K:

```
(④ − ②unfused)  =  (②fused − ②unfused)   +   (④ − ②fused)
   what §9.7          the MESSAGE term          the BYTE term
   measured           (bytes held fixed)        (messages held fixed)
```

Cell ④ is the right control precisely because `FESOM_SPEED_EVPWIDE_FUSE` **cannot** change it —
it already ships one segment, so the knob is a no-op there by construction, and the byte-gate
rung that proves it is a no-op is in the ladder below.

## 2. Correctness predictions (gate, not measurement)

* **P0b.1** — fused is **bit-identical** to unfused at every K, on both backends: the same
  values are packed in the same order into a different address. Anything else is a bug, not a
  result. *(Serial: already PASSED at K=4 and K=8, jobs 26717880 / 26717882, plus std EVP K=2 in
  26717894; re-run on the final binaries is the ladder of record.)*
* **P0b.2** — `EVPWIDE_FUSE=1` under cell ④ is bit-identical to cell ④ **and announces itself as
  a no-op**. A silent no-op and a working lever must not look the same (L80).
* **P0b.3** — the `[evpwide-wire]` line shows **messages/step halved** for ② and **doubles/step
  unchanged**. The bytes are the control: if they move, the fused packing is wrong even if the
  model output happens to match.

## 3. The measurement prediction — and it contradicts the paper's current §8.2

⭐ **I predict fused ② recovers MOST of the ④ − ② gap, i.e. the message-count term dominates and
the byte reading in RESULTS §8.2/§9.7 is wrong.**

The reason is a pattern already in the measured data, which is what makes this a prediction and
not a hunch. Look at how the ④ − ② gap scales with K:

| ④ − ② (pp of model step) | K=2 | K=8 |
|---|---|---|
| farc GPU 4/8/16 N | −3.9 / −4.3 / −3.8 | — / −1.9 / −2.0 |
| dars GPU 8/16 N | −7.1 / — | −2.1 / −2.8 |

Now count what each term does as K grows, per step:

* **extra messages** = (120/K windows) × (1 extra msg/partner) × partners → **∝ 1/K**.
  K = 2 → 8 predicts the gap shrinking by **4×**.
* **extra bytes** = (120/K windows) × 4·Ng(K), and Ng — a K-deep ring — grows roughly linearly
  in K, so the product is **roughly K-independent**. It predicts the gap **not shrinking at all**.

Measured, the gap shrinks by 2–3× from K=2 to K=8. **That is the message term's signature, not
the byte term's.** §8.2 read the ④−② crossing as bytes because bytes were the only term the
pre-registration had named; the K-dependence was in the table the whole time and was not
interrogated.

**Quantitative pre-registration, stated so it can fail:**

| | prediction |
|---|---|
| **P0b.4** (primary) | fused ② recovers **≥ ⅔** of the ④ − ② gap at K=2 on GPU. Below ⅓ falsifies it and confirms §8.2's byte reading. |
| **P0b.5** | the recovered fraction is **larger at K=2 than at K=8** (the message term is the one that decays with K). |
| **P0b.6** | absolute size at dars GPU 8 N K=2: the gap is 7.14 pp, so fused ② should land within ~2.4 pp of ④, i.e. near −2.3 % vs classic instead of +4.9 %. |
| **P0b.7** (CPU) | fusing is worth **less on CPU** than on GPU and is likely unresolvable there: the CPU noise floor is ~1.5 % (§9), and ② already beats ④ on CPU, which is itself evidence that CPU messages are cheap. **A CPU null is pre-declared uninformative** — it will be reported as "below the floor", not as a result. |
| **P0b.8** (fallback, and it is a real outcome) | if fused ② ≈ unfused ② everywhere, the byte reading stands, ② is simply the worse cell, and the honest report is that D1 closed with a negative. That is written here so it cannot be re-described later as anything else. |

**Known ambiguity, declared in advance.** Fusing removes one MPI message per partner but **not**
one pack kernel — the node pack and the σ pack are still two `parallel_for`s. So a null result
at P0b.4 would be ambiguous between "bytes dominate" and "the cost is the pack launches, not the
messages" (L107 says GPU exchange cost is largely launches and packing, charged to *busy*). The
instrumented leg is what separates them: **if fusing pays, `wait` should fall with `busy` roughly
flat; if the residual is launches, `busy` will not move and neither will the step.** No further
build is pre-authorised — a single fused pack kernel would be a new variant, and whether it is
worth building is a decision to take after these numbers, not before.

## 4. Protocol (fixed here, before any leg runs)

* Same-allocation A/B, `jobs/job_m9_ab_gpu`, **min of 2 reps**, leg 1 = `classic` reference,
  every leg `FESOM_SPEED=1`, `io.config.m9_timing`, `PRINT_EVERY=999`. CLEAN legs for the step
  time; a separate `PHST=1` job for the phase split. This is §9's protocol unchanged, so the new
  numbers are comparable with the published table.
* Points, chosen where the ④ − ② gap is largest and best resolved (rep spread there is 0.0–0.5 %):
  **dars GPU 8 N (np32, dt 120)** — the −7.1 pp point, primary;
  **farc GPU 16 N (np64, dt 900)** — second mesh, −3.8 pp at K=2 and −2.0 pp at K=8;
  **farc GPU 4 N (np16, dt 900)** — where ② is at its worst (+5.7 % vs classic).
  CPU: **farc np512** (declared low-yield by P0b.7; run once so the negative is measured rather
  than assumed).
* Legs per job: `classic`, `wide2_kK`, `wide2f_kK`, `wide4_kK` at the K of that job, so every
  comparison is inside one allocation.
* **Every leg's `[m9] mEVP cell:` and `[evpwide-wire]` lines are recorded.** A fused leg whose
  transport line does not say FUSED is discarded, not averaged in.

## 5. What this does NOT do

Not a new physics option: fusing is a transport detail of an option already certified. Nothing
here changes the adoption recommendation, which stays cell ⑤ at K=4 for speed (RESULTS §8.3) —
the exact cells' case is about needing no accuracy argument, and P0b can only change *how much*
they cost, not *what* they compute.
