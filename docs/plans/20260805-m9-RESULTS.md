## 4. Mechanism, measured

nsys, validated per the project's meta-lesson before use: the traced classic→div ratio
reproduces the untraced A/B (+1.76 % vs +1.63 %), while absolute traced step times are 48 %
inflated and were therefore not used.

- Total GPU kernel-busy is **identical** between forms: 21.8 vs 21.7 ms/step.
- The mEVP kernels are marginally **cheaper** in the divergence form: 1.24 vs 1.27 ms/step.
- Of the **8.2 ms** `icedyn` phase at CORE2 np8, only **~1.25 ms is kernel execution**, spread
  over ~480 launches/step. Launch count differs by exactly 3 (the mask kernels): 487 → 490.

**The mEVP subcycle on GPU at this size is launch/exchange-bound, not compute-bound.** That is
why removing whole exchanges (cell ⑤) pays enormously while removing element bytes (cell ③,
`MEVPNOEPS`) pays nothing. It also predicts the regime where Win A could matter: many fewer,
much larger kernels — i.e. far larger per-rank workloads than anything reachable here.

## 5b. farc at thousands of ranks — the configuration Koldunov et al. (2019) diagnosed

`/pool/data/AWICM/FESOM2/MESHES_FESOM2.1/farc` (638 k nodes, 47 levels), dt=900, 100 steps,
CPU, rank ladder 512 → 2304 (that mesh copy's partition ceiling). **This is the same mesh as
GMD 12, 3991 (2019) §Fig. 7**, which reports sea ice growing from **16 % of runtime at 144
cores to 33 % at 6912**, blames one halo exchange per EVP subcycle (~100/step) with too little
arithmetic to amortise the MPI, plus cores without ice idling in `MPI_Wait`, and proposes —
untested at the time — **"wider halo regions to reduce communication frequency"**. Cell ④ is
that proposal implemented exactly; cell ⑤ is its cheap approximation.

**Ice share of the step** (ice + icedyn + iceadv, busy **and** wait, matching the paper's
definition — quoting `icedyn` busy alone undercounts it by ~3×):

| ranks | 512 | 1024 | 1536 | 2048 | 2304 |
|---|---|---|---|---|---|
| ice share | 11.4 % | 11.4 % | 12.6 % | 12.9 % | **13.2 %** |
| lag8 → model step | −1.1 % | −1.8 % | −1.2 % | −1.6 % | **−3.4 %** |
| lag8 → icedyn busy | −11.0 % | −8.6 % | −10.2 % | −12.8 % | −14.3 % |

The share **grows with core count, in the same direction as the paper**, but is lower in
absolute terms (13 % at 2304 vs the paper's ~25–30 % interpolated there) and rises more slowly.
Two candidate reasons, neither tested: the port has had a long comms-optimisation campaign
(CGPIPE, fused halos, device-resident state) that the 2019 FESOM2.0 had not; and these runs use
mEVP where the paper used standard EVP.

### ⭐ The mechanism is confirmed, and it is `MPI_Wait`, not kernel time

np2304, classic → lag8, from the same instrumented run:

| phase | busy | **wait** | mpi/step |
|---|---|---|---|
| `icedyn` classic | 3.5 ms | **4.8 ms** | 240 |
| `icedyn` lag8 | 3.0 ms (−14 %) | **1.9 ms (−60 %)** | 30 |
| `ocean`, `cg` | unchanged | unchanged | unchanged |

Total ice cost 8.3 → 4.9 ms (**−41 %**); whole-model MPI ops/step 987 → 777 (the −210 is
exactly the saved ice exchanges). **The lever pays by removing idle, not by computing faster** —
precisely the mechanism the 2019 paper identifies. The exchange count drops exactly 8× (240 →
30), which is also the knob-fired proof.

Note what this implies for cell ③: the divergence form is ~0 on farc at every rank count
(−1.4 % … +1.0 % on `icedyn`), because it changes kernel work, and kernel work is not what costs.

### Where the ceiling is

At np2304 `cg` (the SSH solver) carries **21.7 ms of the 43.7 ms total wait** — five times the
ice phase's wait after lagging. So on this mesh, past ~2000 ranks the dominant imbalance is the
SSH solve, not the ice. That bounds what any ice lever can deliver here and matches the paper's
observation that "SSH and sea-ice calculations become more expensive than the 3-D part".

### Two defects the byte gate caught and inspection did not

Cell ② was bit-identical from the first run while ④ failed at 3.0e-4 in `a_ice`; that
asymmetry — same rings, same ship, same maps, same solve tail — is what localised both.

1. **The ghost gather was timed wrong, and raced.** ④ stores no element stress, so its gather
   must recompute it from `u_aux` — but it sat inside the ghost *node* kernel, which runs after
   the owned node solve has already overwritten `u_aux` at every owned node. It recomputed from
   post-solve velocities where the owner had assembled from pre-solve ones. The same kernel also
   read `u_aux` at other ghost slots while writing `u_aux` at ghost slots: a real read-write
   race, benign-looking on Serial and nondeterministic on CUDA. Fixed by staging the gather in
   its own pass between the owned element kernel and any node update. **Cell ② is immune by
   construction** — its stress is computed and *stored* by the element pass, so reading it later
   is safe. → **L106**.
2. **The ghost node mask was a scatter where it had to be a gather.** It looped ghost *elements*
   and set `nod_el` at their three vertices — and a ghost element's vertices include *owned*
   nodes, so it reached back into owned state. Now each ghost slot asks the owner's question
   with the owner's data (does any element of my gather row carry ice?), which is ghost-only by
   construction. This one did not change the failing bytes — defect 1 dominated — but it was
   wrong on its own terms.

### 8.1 What they cost — and the honest headline is that EXACTNESS IS NOT FREE

GPU CORE2, dt 1800, 300 steps, CLEAN legs, all six cells in the same allocation (26712790 /
26712791 / 26712926). Change in **model step** vs classic:

| | 2 N (np8) | 8 N (np32) | 16 N (np64) |
|---|---|---|---|
| classic (s/step) | 0.0615 | 0.0763 | 0.0885 |
| **⑤ lag8** (approximate) | **−15.3 %** | **−20.8 %** | **−25.5 %** |
| ② wide K=8 (exact) | +0.3 % | −7.7 % | −12.5 % |
| ④ wide K=8 (exact) | +2.0 % | −8.4 % | **−15.3 %** |
| ② wide K=4 | +1.0 % | −5.1 % | — |
| ④ wide K=4 | +3.1 % | −5.5 % | — |

**The exact wide halo delivers roughly half to 60 % of what the one-line approximation does,
and at 2 nodes it delivers nothing at all.** That is not a disappointment to be explained away —
it follows directly from §4's measured mechanism. The mEVP subcycle is **launch/exchange-bound**,
and the two cells do opposite things to the launch count: cell ⑤ removes exchanges and adds
*nothing*, while cells ②/④ remove the same exchanges but add two to three ghost kernel launches
per subcycle plus the ghost arithmetic. At small rank counts the added launches cancel the
removed messages exactly; the exchange term only wins as rank count grows.

Both exact cells' gains **grow monotonically with rank count** (② 0 → −7.7 → −12.5 %,
④ +2.0 → −8.4 → −15.3 %) and the gap to cell ⑤ narrows with scale (16 N: −15.3 % vs −25.5 %,
i.e. 60 % of it). Extrapolating that trend past 16 N is exactly the kind of guess this project
does not make — it wants the measurement.

### 8.2 H3 answered, and this is where Danilov's reformulation finally pays

> reading below was the only decomposition available while ② shipped two messages; the fused

The pre-registration's H3 said ② − ④ is dominated by the **2× byte ratio** (8·Ng vs 4·Ng).

| | 2 N | 8 N | 16 N |
|---|---|---|---|
| **④ − ②** (percentage points of the model step) | **−1.6 pp** (④ worse) | **+0.7 pp** | **+2.7 pp** (④ better) |

**The divergence form loses at small scale and wins at scale, and the crossing is the result.**
④ ships half the bytes but pays one extra gather pass; where the message dominates (16 N) the

This matters for how the whole study reads. **H1 was falsified** — the reformulation buys

what it does to the *communication*: it makes everything carried a node quantity, so the wide
halo needs one segment of 4·Ng instead of two totalling 8·Ng. §8.1–8.2 is the first measurement
in this campaign where that pays, and it pays only in the regime the reformulation was aimed at.

### 8.3 What this means for the recommendation

For **speed alone, cell ⑤ at K=4 remains the option to use** — it is worth more than the exact
cells at every rank count measured, and §5 characterises its accuracy cost (inside mEVP's own
floor, 1.2–1.5× at K=4). Cells ②/④ are the right choice for anyone who wants the exchange
reduction with **no accuracy argument whatsoever**, and their case strengthens with rank count.

### 10.4 Mechanism, and the pre-declared ambiguity is resolved

The pre-registration named an ambiguity in advance: fusing removes an MPI message per partner but
**not** a pack kernel, so a win could have been messages *or* the residual could have been pack
launches (L107). The instrumented leg decides it — dars GPU np32, K=2, `icedyn` phase (ms):

| leg | busy | wait | model step |
|---|---|---|---|
| classic | 14.9 | 20.8 | ref |

**Fusing pays in `wait` (23.6 → 12.5 ms), not in `busy` (20.0 → 16.7).** So the second message

### 12.2 What was built — `FESOM_SPEED_EVPWIDE_LEAN=1`

Opt-in, default off, requires `EVPWIDE=K` (aborts otherwise — a lean knob without a wide halo
would be a dead knob wearing a live name), incompatible with `MEVPDIV_SELFCHECK`.

1. **One kernel per stage over owned+ghost**, `_g` arrays selected by an index branch, with
   **raw pointers** in the closure (~300 B ⇒ local-memory path). This is the structure of
   Danilov's `ice_mevp_double.F90` — one loop, widened bounds — reached the only way a
   separate-array port can reach it.
2. **The owner-order gather is dropped.** Ghost nodes are assembled by the same unguarded atomic
   scatter owned nodes use, so the difference against the exact path is a summation *order*.
   In the divergence form this also deletes `maevp_gather_div_w`'s ~6× redundant
   per-(ghost node, incident element) stress recompute, and makes both L106 defects structurally
   impossible (an element kernel that scatters runs before any node kernel and writes no `u_aux`).
   The ghost half of the scatter still stops at `n < myDim`, so an owned node's rhs stays exactly
   what the owned assembly over `[0,Eo)` defines it to be.
3. **The once-per-step ghost maps are left EXACT** (`aux_init_w`, `node_pre_w`, `elem_pre_w`,
   `nod_has_el_set_w`): 4–5 launches/step out of 363. The prize is the 360.

⭐ **The design assumption is checkable from the binary, without a run** — and it holds:

```
cuobjdump -symbols <bin> | c++filt | grep cuda_parallel_launch_<path>_memory \
                                   | grep -c 'ParallelFor<fesom_ice_evp_dynamics_m_kk('

  b_509a5771 (exact only)          9              24
  b_94617f1d (+ 5 lean kernels)    9              29
```

All five fused kernels instantiated on the **local-memory** path; the constant-memory count did
not move. Worth knowing as a technique: which launch path a Kokkos kernel took is a static
property of the closure and is visible in the symbol table, so it can be checked at build time

### 12.4 The ship audit — Danilov's "11 fields is too much", answered from the wire

`FESOM_EVPWIDE_SHIPCHK=1` (`jobs/job_m9_shipchk`, 26740589/90, CORE2 np8 Serial): per field, the
max difference between the **arriving owner byte** and **what this rank already holds**, over the
slots inside FESOM's own dist-file halo. Session 4 measured what the ship *costs*; this measures
whether it is *necessary*, which is the question that decides whether it can be trimmed.

**9 of the 11 fields come back at exactly 0.000e+00** — `uice`, `vice`, `a_ice`, `m_ice`,
`m_snow`, `u_w`, `v_w`, `sax`, `say`. FESOM's ordinary halo exchange has already put the owner's
bytes there. **`rhs_a` and `rhs_m` do not** (1.0e7–4.0e7 from step 2 on): they are assembled and
area-scaled over owned nodes only — trap 7 — so a halo slot has no correct local value at all.

⚠️ **But redundancy only reaches ring 1.** The extended slots (BFS rings 2..R) have no other
writer in FESOM at any K, so their 11 fields can never be trimmed:

| K | halo slots (trimmable) | extended slots (not) | trimmable share of the prestep ship |
|---|---|---|---|
| 2 | 1382 | 1638 | 9 × 1382 / (11 × 3020) = **37.4 %** |
| 4 | 1382 | 5173 | 9 × 1382 / (11 × 6555) = **17.2 %** |

and the prestep ship is itself **1.6 % of messages and 5.4 % of doubles** (K=4, from
`[evpwide-wire]`). ⇒ **the trim is worth ≈0.9 % of the wide halo's wire volume at K=4 and no
messages at all.** So the answer to the objection is: *nine of the eleven fields are indeed
redundant, on ring 1, and removing them buys under one percent of the traffic* — it was not
built, and this is the measurement that says why rather than an assumption that it would not pay.
The audit knob is in the tree so the number can be re-taken on any mesh.

Monotone in K in both forms on both meshes, exactly as the exact cells were (§9: "K=2 is the WORST
K for ②/④, they improve K=2→4→8"). **This was not a foregone conclusion** — the term the lean
writing removes is *launches*, which is K-independent, while the ring's arithmetic grows with K,
so the optimum could have moved down. It did not: **K=8 remains the recommendation, now measured
for the lean path rather than inherited from the exact one.**

⭐ And the divergence form's lead is **not an artefact of one K**: it is positive at every K on
both meshes (CORE2 0.6 / 0.0 / 0.7 pp at K=2/4/8; fArc 2.2 / 2.7 / 1.5 pp), which is the
robustness check §12.6c's rehabilitation of H3 needed.

⭐⭐⭐ **The launch structure was worth 5.6× the algorithm.** At CORE2's own operating point the
exact wide halo is worth −2.4 % of the model step — the point at which session 2 concluded the
exact cells "buy nothing at small node counts". Folding the same computation into the loops that
already exist takes it to −13.6 %. Nothing about the numerics changed: the ring is still computed,
the same messages are still removed, and the difference between the two rows is 360 kernel
launches per step.

🔴 **The control that makes this a compute result and not a comms one:** `[evpwide-wire]` reports
**exactly the same traffic** for a lean leg and its exact twin — ② 390.5 msgs/step and 1 542 053
doubles/step in both, ④ 390.5 and 931 929 in both. Not one message or one double moved. The whole
−11.5 pp is on the compute side.

⭐⭐ **On the model step the two forms come out level here — 0.0570 both, from independent reps
(0.0572/0.0570 and 0.0570/0.0570), with the `[m9]` provenance line confirming cell ② and cell ④
respectively in each** — against +3.5 pp apart in the exact build. In the ice-cost currency they
are not quite level (④L 1.9 pp ahead), and on fArc the gap opens to 6.5 pp with the ordering
flipped relative to the exact build. **See §12.6c: the launch structure was masking the divergence
form's advantage rather than creating it.**

**fArc, CPU, 512 ranks / 4 nodes, model step (26740857/58):**

|---|---|---|---|
| classic | 0.2391 | — | |

⚠️ **On CPU the lean structure is a loss in the classic form and a win in the divergence form**,
and the two signs have the same mechanism. The lean path trades a *gather of plain reads* for an
*atomic scatter*. In the classic form that is all it does — the gather was only re-reading stored
`sigma` — so the added atomics over the ghost elements are unpaid and it loses 5 pp. In the
divergence form the gather also had to **recompute each incident element's stress once per
(ghost node, element) pair**, about 6× over, because it could not scatter; deleting that pays for
the atomics and 3 pp more. So on CPU the lean form **reverses the ranking of the two cells**:
④L (+15.56 %) now beats ②L (+16.60 %) and ②exact's +11.00 % stays the best exact row.

Neither CPU row is a recommendation — the exact wide halo already costs +11…+19 % there (L107:
the ring zone is comparable to the rank's own subdomain at 512 ranks and adds a new imbalance).
What the CPU pair contributes is the **decomposition**: it isolates the atomic-scatter term and
the redundant-recompute term from the launch term, which the GPU alone cannot separate.

### 12.7 The lean trace — the design assumption confirmed end to end (26740859)

Same protocol as §12.1 (fArc np16, 20 steps, K=8), third leg added:

| per model step, ice-dynamics region | classic | wide ② exact | **wide ②L LEAN** |
|---|---|---|---|
| mEVP launches, **local**-memory path | 487 | 488 | 488 |
| mEVP launches, **constant**-memory path | 0 | **362** | **2** |
| exchange pack/unpack launches | 262 | 84 | 84 |
| total launches in the region | 749 | 934 | **574** |
| GPU **busy** | 4.552 ms | 6.315 ms | **4.020 ms** |
| inter-kernel **gap** | 3.617 ms | 10.191 ms | **1.443 ms** |
| region total | 8.169 ms | 16.506 ms | **5.463 ms** |
| model step (under nsys) | 0.1804 s | 0.1608 s | **0.1551 s** |

The 362 constant-memory launches became **2** — the once-per-step ghost maps deliberately left
exact (§12.2). The region costs **−67 % against the exact wide halo and −33 % against the classic
every-sub-cycle baseline**.

⭐ **And a second-order effect worth the lesson: the OWNED kernels sped up too.** Their median
gap-before falls 5.47 µs (exact wide) → **1.31 µs** (lean), below even the classic build's 4.38 µs.
The constant-memory staging was not only slow for the kernel using it; it serialised the launches
around it. That is why the lean region beats the every-sub-cycle baseline it was only meant to
match — it is not doing less arithmetic (busy 4.020 vs 4.552 ms is mostly the removed halo packing),
it is dispatching without stalls.
