## Overview

The port's golden rule so far was bit-identity to the validated C port. That rule is now **relaxed by user decision**: floating-point rounding/summation-order changes, solver-path changes, and (as a reserve) small physics-visible scheduling changes are all allowed, provided results stay climate-valid under a defined gate. **Single/mixed precision is explicitly banned — everything stays FP64.** Repartitioning is **out** (user tried work-weighted partitions; it did not help and the tooling is poorly documented).

**Goal:** raise the GPU-node vs CPU-node ratio from ~3.6× to **≥5.0× (stretch 8×)**, staged:
- **Stage 1 (sweet spot):** NG5/dars @ 4–8 GPU nodes from 3.6×/2.9× to ≥5× (4N is the firm target; ≥5× at 8N is the stretch edge of Stage 1 — the comm/sync share, hardest to cut, grows there).
- **Stage 2 (scale):** flatten the ratio decay toward 16N (today 2.5×); honest reporting of the 32N ceiling (CPU strong-scales at 96–98% efficiency — a ≥5× ratio at 32N is likely physically unreachable).
- **Expected production outcome:** ~2 SYPD @ dt240 on NG5 at 16–32N in pure FP64 — the target mixed precision was supposed to buy.

**Baseline (M5.24, `docs/SCALING_M524.md`):**

| NG5 | 4N | 8N | 16N | 32N |
|---|--:|--:|--:|--:|
| GPU s/step | 1.273 | 0.810 | 0.492 | 0.374 |
| CPU s/step | 4.599 | 2.356 | 1.237 | 0.631 |
| **ratio** | **3.6×** | 2.9× | 2.5× | 1.7× |

**Step budget NG5@4N (`docs/PROFILE_M522.md`):** GPU kernels 46% (FCT 20.3%, EOS 9.9%, mixing 6.2%, ice_dyn 6.1%, SSH 5.6%, ALE 4.1%, trdiff 2.9%, GM 2.6%), halo load-imbalance ~10%, true comm 4.6%, PCIe ~3%, **remainder ~25–30%** = launch gaps + ~880 device fences/step + blocking-sync stalls. **At 16N-class per-rank size (dars@8N proxy, 99k verts/rank):** halo Waitall 37% of step (63% of that = imbalance), CG 12.5%.

**Dead levers (do not revisit):** CG warm start (already warm-starts from `d_eta`, `fesom_ssh.cpp:806`); device FMA (nvcc `--fmad=true` is already on; only host contraction is off via `-ffp-contract=off`, `CMakeLists.txt:53`); PCIe (659 MB/step, forcing-only); comm/compute overlap (ceiling 4.6%); persistent MPI requests (L2 dead end on Levante); repartitioning (user-tested, no gain).

## Development Approach

- **Testing approach: Regular** — in this project "tests" = the gate ladder, not unit tests (no unit framework exists; the model IS the test). Every task's test checkboxes are gates.
- **Knob rule (the M6 rule, unchanged):** every lever ships behind `FESOM_SPEED_<NAME>` (default OFF). **Knob-OFF is byte-identical to certified HEAD at every commit**, gated by `diff_snap.py` vs `/work/ab0995/a270088/port2/m6_baseline_serial/`. `FESOM_SPEED=1` = master switch enabling all blessed levers; per-lever knobs override.
- **Serial stays legacy:** perf knobs act on the CUDA path only; the Serial backend keeps the bit-identical-to-C path forever (debug oracle, Z7-trap mitigation). Exception for validation: bit-id-claimed levers get a dev-only `FESOM_SPEED_FORCE_SERIAL=1` run where the levered code runs on Serial and must `diff_snap` == baseline — the **strongest possible proof** that a lever is pure re-execution.
- **Kill-fast:** each lever has a payoff regime; a flat same-alloc A/B there → revert the same day (precedent: L2, pressure_bv fusion).
- **Measurement discipline:** ±10% inter-allocation noise → all A/Bs same-day, same-allocation, both binaries in one job (the `job_dars_l3_ab` pattern); 35 steps, 2 reps, min, `snap_every=-1`; dt180 measured, SYPD reported @dt240 with the ×1.03 CG correction (re-derived once the CG levers land — Task 3.4). Per-lever A/Bs go in the Lever log of `docs/GPU_SPEED_M7.md`; the ratio ledger (full standard set) is refreshed at tier boundaries and whenever a standard-set re-measure runs.
- **Commit rhythm per lever:** implement → racecheck/sanity → CORE2 fidelity gate → same-alloc A/B → ledger → commit (with knob-OFF byte gate green) → next.
- Complete each task fully before the next; update this plan file when scope changes.

## Technical Details

- **Ratio metric:** ratio(N) = s/step(`build-m7serial`, 128 ranks/node, knobs OFF) ÷ s/step(`build-m7cuda`, 4×A100/node, knobs as stated); both sides same day. CPU baseline stays knob-OFF (levers are CUDA-path-only, so the CPU number is the certified code by construction).
- **FORCE_SERIAL byte proof:** for levers claiming bit-identity, a dev-only env forces the levered code path on the Serial backend; `diff_snap.py` vs `m6_baseline_serial` must be rc=0. This proves "pure re-execution" stronger than any statistical gate. Levers that can't pass it are reclassified gate-class — that's fine, but the claim must be tested, not assumed. **Precondition for the proof to transfer to CUDA:** the lever's kernel source must be backend-identical (no `#ifdef KOKKOS_ENABLE_CUDA`-divergent kernel bodies); the Tier-1 levers satisfy this — check it per lever.
- **Fence-removal correctness:** Kokkos-CUDA `parallel_for`s on the default stream execute in issue order; the post-unpack fence at `fesom_halo_device.cpp:286` only orders device work vs HOST access. Removal is safe iff no host reader follows before the next natural sync. The pre-MPI fence (`:251`) MUST stay (MPI reads the device buffer from host-posted calls).
- **Chronopoulos–Gear CG:** recurrences computed so p·Ap, r·z, and the norm share ONE Allreduce; extra axpy per iter; identical convergence theory, reassociated sums → gate-class. Fallback to plain CG via knob at runtime.
- **Chebyshev precond:** M(x) ≈ A⁻¹ via degree-k Chebyshev on [λmin, λmax] of the Jacobi-scaled A; SPD-safe with CG as long as the polynomial is fixed per solve (it is; bounds re-estimated only at init). Each apply adds k SpMV+halo but removes ~k× iterations ⇒ Allreduce count (the 16N latency killer) drops ~k×.
- **EVP compaction:** list build is two `parallel_scan`s (elements, nodes) + one full-mesh zero/BC kernel per step; 120 subcycle kernels then run on ~5–20% of entities. Halo messages unchanged (full uice/vice fields) — this lever cuts compute + imbalance, not messages.
- **Wide-halo EVP:** dependency cone grows 1 element-ring per subcycle; with k-ring halos and shrinking iteration sets, all consumed values are locally identical to the 1-ring schedule (redundant ghost compute). The rhs scatter at the shrinking boundary is the one subtle spot — handled by including ring-(k−j) elements in the scatter set so every kept node receives all its contributions.
- **Memory:** FCT2 second-tracer scratch = plausibly 3–5 nod3D arrays (LO solution, ± antidiffusive fluxes, R± limiters), i.e. ≈3–5 GB/rank at NG5@4N (1.04 GB per array) — VERIFY the exact count at implementation; edge-flux arrays for scatter-variant-2 ≈ edge3D-sized, ~0.7 GB/rank NG5@4N. A100-80GB headroom confirmed in M5.x (steady-state ~20 GB/rank).
- **SLURM:** gpu partition `--ntasks-per-node=4 --gres=gpu:4`, compute partition 128 ranks/node; job names `m7_*`; outputs only under `/work/ab0995/a270088/port2/m7/`.
- **NG5 cold-start caveat:** 35-step timing windows are safe ≤32N (blowup ~step 155 at 32N); never gate correctness at 32N; climate gates are CORE2-only (established refs).
