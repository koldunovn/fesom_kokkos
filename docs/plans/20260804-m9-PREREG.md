# M9 pre-registration — divergence-subcycled mEVP

*Committed BEFORE the first fleet job (L93). Written after Stage-1 certification, so the
hypotheses below are calibrated against measured numbers rather than guessed — but no
performance A/B has been run yet.*

Binaries of record: `/work/ab0995/a270088/port2/m9/bin/s1/` — Serial `2044312e`, CUDA
`368c5674`. One binary per backend; every cell is knob-selected, so no build variance between

## 1. Protocol of record

- **`icedyn` phase time is primary; SYPD is reported beside it, never instead of it.**
- The two never come from the same run: `icedyn` from **matched instrumented** legs
  (`FESOM_SPEED_PHASESTATS=1`), SYPD from **clean** legs. Measured instrument cost at CORE2 np8:
  2.2930 vs 2.2902 s/step (+0.12 %), single rep on different nodes — small, but the split stands.
- 300 steps, min-of-2 reps, all legs of a comparison in **one allocation**, same day.
  `-C a100_80` on every GPU absolute (L94).
- 🔴 **Every CPU leg exports `FESOM_SPEED_FORCE_SERIAL=1`.** Without it the Serial backend
  vetoes every `FESOM_SPEED_*` lever — 15 of them, PHASESTATS and all M9 knobs included — and
  the entire CPU half of the study returns 0.00 % differences. Verified the hard way (26697195).
- Every leg prints its `[fesom_speed]` announces and its `[m9] mEVP cell:` line. A leg whose
  cell line does not name the intended cell is discarded, not interpreted.
- `BIN=` pinned to a frozen binary on every job.

## 2. What is already measured (the calibration, not a prediction)

CORE2 np8, CPU, 300 steps, `FESOM_SPEED=1 + FORCE_SERIAL=1` (job 26697663):

| phase | busy min/mean/max (ms/step) | wait mean | mpi/step |
|---|---|---|---|
| icedyn | 12.8 / **73.7** / 211.8 | 137.8 | 240 |
| ocean | 1524 / 1734 / 1867 | 172.9 | 68 |
| TOTAL | 1821 / **1959** / 2061 | 339.3 | 670 |

So `icedyn` is **3.8 % of busy**, ~9 % counting its wait, and it is **imbalance-dominated**
(16× spread across 8 ranks; rank 0 waits 199 ms). CORE2 np8 CPU is 88 % ocean.

**Consequence, stated up front: this configuration cannot show a convincing SYPD effect for any
ice-dynamics lever.** A 20 % `icedyn` win is ~0.8 % of the step. That is not a defect of the
lever, it is why `icedyn` is the headline metric.

## 3. Hypotheses

**H1 — Win A (③ vs ①) is a memory-operation reduction that converts to time only where the
element kernel is bandwidth-bound.**
The element kernel loses 3 element loads + 3 element stores per element per subcycle (48 B/elem
in fp64) out of roughly 200 B/elem of streamed traffic ⇒ **≈24 % fewer element-kernel memory
operations**. The node kernel gains an `R` read-modify-write (32 B/node, on ~half as many
entities).
- Predicted `icedyn`: **−5 … −15 %** where the working set exceeds cache; **≈0 %** where it does
  not.
- 🔴 **Falsifiable sub-prediction (the important one): Win A ≈ 0 at CORE2 np8 on BOTH backends**,
  because the σ working set is only 3 × ~31k elem × 8 B ≈ **0.74 MB/rank** — comfortably inside
  Zen3 L3 and A100 L2. Win A should grow with per-rank workload and appear only once σ stops
  being cache-resident. A 15-step GPU sanity line already showed −0.67 % (i.e. nothing) at this
  config, consistent with this.
- If Win A is ALSO ≈0 at the largest per-rank workloads we can reach, the honest conclusion is
  that σ is cache-resident at every realistic decomposition and Win A is an instruction-count
  effect, not a bandwidth one. That is a publishable negative and will be reported as such.

**H2 — Win B (⑤/②/④) grows with rank count.** Exchange count 120 → 120/K (+1 for the wide
prestep). Biggest at 16–32N on core2/farc, smallest at low node counts.

**H3 — ② − ④ is not pure communication.** It decomposes as
`(bytes 8·Ng → 4·Ng) + (messages 2 → 1, only in the UNFUSED build) + (ghost-share × per-row
Win A)`, the last because ②'s ghost element kernel does the σ read-modify-write that ④'s does
not. Per-row Win A comes from `③ − ①`; ghost share from the build summary. Per D1 both ②-fused
and ②-unfused are built, so the message term is isolated rather than assumed.

**H4 — the banked negative.** std-EVP EVPWIDE delivered **−2.2 % of total at 16N, K=8** against
a −27 % pre-registered ceiling. Expect that order at model level here.

**Floors: 0 for every win.** Redundant ghost compute, larger messages and new partners eat some.
History: five consecutive M7 pre-registrations measured wrong-LOW (L93) — do not adjust on
harvest; run the L94 checklist instead.

**The punchline being tested:** H1 and H2 depend on per-rank workload in *opposite* directions,
and the divergence form is the only cell that collects both.

## 4. Decision rules (fixed now)

- K\* = argmax measured `icedyn` reduction at the largest rank count, with no regression at the
  smallest. Adopted **OPT-IN** regardless of size; promotion is the user's call after a climate
  leg.
- A cell qualifies for an L6 climate leg only if it wins `icedyn` by >5 % somewhere in the
  sweep AND its L3 ice-field differences sit at or below the mEVP scheme floor.
- ⑤ (lagged) is reported with its accuracy cost attached at every K. It is never presented as a
  speed result alone.

## 5. Deviations and caveats to disclose in any write-up

1. **Cell ③ is not literally Sergey's F90.** He folds `inv_mass` into R; we store R unscaled and
   apply `mass` at use, because folding it in makes the carried state remember a *previous*
   step's mass scaling. The reformulation is his; this detail is ours.
2. **②'s message-count penalty is implementation-dependent** (D1). Both segments already loop the
   same `S.partner` vector, so node and element data *can* be concatenated into one send. The
   intrinsic advantage of the divergence form is the 2× byte ratio.
3. **The mask-flip non-equivalence is real and measured** at 2.1e-11 relative (20-step CORE2),
   firing only on steps where `ice_el` membership changes.
4. `FESOM_MEVPDIV_SELFCHECK` perturbs the trajectory (it re-baselines R each step) and is never
   a timing or L3 leg.
5. The σ host↔device rails are skipped under `MEVPDIV`; R has no rail. Timing legs additionally
   run `FESOM_SPEED=1` (ICERAILS ⇒ no rails at all), so no cell is credited for skipped PCIe.
