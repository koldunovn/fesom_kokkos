## Three corrections this session made to its own earlier claims

1. **"The ordering gain shrinks with rank count"** (session 1, repeated by me) is **falsified**:
   256/512/864 = −2.42 / −1.51 / −2.23 %. Not monotone. Safe statement: −1.5…−2.4 % on CPU at
   every rank count, −1.5…−4.9 % on GPU, and it does **not** decay with scale.
2. **`commvol_max_rank` is seed noise at the 10–17 % level** (Finding 18), which retires this
   session's own fArc "−18 %" headline. Rank arms on sums: cut, total comm volume, off-node
   volume, halo, element replication.
3. **The renumbering lever is not universal** (Finding 17). CORE2 is the only mesh in the set
   whose numbering is arbitrary; fArc, dars, NG5 and FORCA20 all ship at 88 % element-gather
   locality and every space-filling curve makes them worse.

## The three things a reader must not re-derive

1. **The day-1 CPU-256 race and every day-1 gate leg used the wrong baseline** (shipped mesh vs
   settled partition, one node different). Corrected: hil −2.42 %, rcm −2.24 %, and day 1's
   "RCM ahead everywhere" does not survive the repeat — the gap is inside same-day noise.
   A precheck now runs inside every race job and refuses non-pure-ordering arms.
2. **The accuracy floor is the SSH solver's stopping criterion, not machine epsilon.** A leg that
   keeps the CG iteration path identical stays at 4.5e-12 of the field rms; any leg that changes
   the path lands at 3e-4…6e-3. No accuracy gate on this model can be tighter than that for a
   decomposition or numbering change.
3. **`isolated_nodes == 0` is not a convergence criterion.** CORE2 864 holds a node that no move
   can repair. Use idempotence — a pass that moves nothing.
