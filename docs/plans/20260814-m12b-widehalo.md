## Overview

The SE barotropic block (`FESOM_SSH_MODE=se`) performs **two tiny halo exchanges per substep** —
η over `NOD2D`, Ū over `ELEM2D` — with M = 20…90 substeps per baroclinic step. At CORE2 16N GPU
that block is 7.8 ms busy + **11.8 ms MPI wait** of an 84 ms step; NG5 64 GPU is 32 % wait.
The wait is now the dominant removable cost of the scheme.

This plan builds the **K=1 rung**: compute η redundantly on the ring-1 (eDim) nodes instead of
receiving it, and exchange only Ū — over the *existing* `com_elem2D_full` list. **Two exchanges
per substep become one** (measured: messages/substep ×0.500–0.513 at every point, because
`com_elem2D_full` reaches the *same partner ranks* as `com_elem2D`), and no new index space or
comm list is required. The per-substep path needs **no new transport code**; the one-shot
operator-row handshake in Task 3 does — it ships variable-length `(gid, coefficient)` payloads,
which the `real_t`-only, fixed-stride halo layer (`fesom_halo.h:40`) cannot express.

⚠️ **The rung was designed as a bitwise transformation and is not one** — not because of anything
it does, but because the certified SE module computes ~0.55 % of elements on more than one rank
and never reconciles them, so the baseline's η encodes which rank owns each node. See the FINDING
section: the rung is exact (≡ 0.0) wherever the model's own Ū is rank-consistent, and the residual
elsewhere saturates ~400× below the floor the SE track already judges CUDA runs against.

Deeper K (exchange once per K substeps, rim shrinking by one ring per substep) is **not built in
this plan**. It is designed here as the *extended-mesh contract* (Technical Details §D) and gated
on the K=1 numbers plus the Gate-0 skew/transport split — a deliberate decision recorded in
Task 8, not an omission.

Benefits: fewer synchronisation points per step on the path that is 60 % wait; an exactness gate
that holds wherever the model itself is rank-consistent, with the residual measured rather than
assumed; and the groundwork (contract, census tooling, cost model) for the second customer —
higher-order advection — without paying for an abstraction that the measurements may not justify.

1. **Containment holds everywhere.** On all 11 points, **0** elements incident to a ring-1 node are
   missing from the local element list: `eDim_elem2D + eXDim_elem2D` *is* element ring 2, and
   `com_elem2D_full` is exactly the list the K=1 rung needs. (Still asserted at runtime — no
   partition we have not measured gets to be trusted.)
2. **The `elem_nb` eXDim hazard does not fire.** `se_build_operators` takes viscosity neighbours
   straight from `edge_tri`, which *could* name an element in the eXDim tail while `Ubt` is
   allocated only over `myDim+eDim` — an out-of-bounds read. Measured count over all 11 points:
   **0**. Not a live bug; retired by construction in Task 2 (full-extent allocation) and asserted.
3. **The rim shrinks by ONE ring per substep, not 2K−1.** In the census BFS's own ring definitions
   (`m12b_ring_census.py`: element ring *r* = elements first reached from node ring *r−1*, so
   elements incident to node ring *j* lie in element rings ≤ *j*): with Ū valid to element ring E
   and η to node ring D, η^{m+1} is valid wherever its incident elements are (D′ = E), and
   Ū^{m+1} on element ring *i* needs η at its vertices (node rings ≤ *i*, satisfied) **and** Ū at
   its edge-neighbours (element ring *i*+1), giving E′ = E−1. mEVP needed 2K−1 because it carries
   element σ across substeps; SE's η/Ū alternation does not. **K substeps need K rings.** The
   handoff's "R = 2K−1, K=8 start" inherits mEVP's arithmetic and overstates the cost by ~2×.
   ⚠️ The edge-neighbour term is the *viscosity* gather (`fesom_ssh_se.cpp:857-877`), so
   `FESOM_SE_VISC=0` has a different shrink law — worth one cheap check before any deep-K sizing,
   since it bounds the deep-K cost from below.
4. **Deep-K cost is cheapest where the mesh is biggest per rank** (cumulative node zone / owned):

   | point | K=2 | K=4 | K=8 |
   |---|---|---|---|
   | NG5 64 GPU | 0.02 | 0.05 | **0.10** |
   | CORE2 64 GPU | 0.13 | 0.30 | 0.66 |
   | farc 2048 CPU | 0.44 | 1.01 | 2.40 |
   | dars 8192 CPU | 0.59 | 1.30 | 3.02 |

   So deep K is nearly free at NG5/dars GPU, affordable at CORE2 16N GPU, and hopeless at the
   big-CPU points — Sergey's "on CPU it is just the doubled halo", as a number.
5. **The SE kernels are launch-bound at the GPU points.** CORE2 16N: 7.8 ms busy / 50 substeps =
   156 µs per substep over ~7 launches ≈ 22 µs each at 1982 nodes/rank. Widening a `RangePolicy`
   is therefore close to free *provided no launch is added* — the M9 LEAN rule (L109).
6. **Messages really do halve — measured, not assumed.** The headline is a claim about *partner
   counts*, so it was checked: `com_elem2D_full` has the **same `rPEnum`** as `com_elem2D` and
   `com_nod2D` at every point (it reaches the same ranks with more entities each), so
   messages/substep go ×0.500 (CORE2 16/64, farc 64, NG5 64) to ×0.513 (farc 2048) / ×0.505
   (dars 8192). Bytes/substep rise ×1.34–1.49.
7. **A ring-1 CSR row cannot be assembled locally at any precision.** 42.5 % (CORE2 dist_64) and
   43.5 % (farc dist_2048) of the edges incident to a ring-1 node are **not in the local edge
   list** (`myDim_edge2D + eDim_edge2D`) — an edge joining two ring-1 nodes touches no owned node.
   Shipping the owner's row is therefore a *necessity*, not a precision preference. (An earlier
   draft justified shipping by EVPWIDE v3's vectorised-`cos`/`tan` hazard; that is the right rule
   for *geometry*, but `se_build_operators` has no transcendentals — `fesom_ssh_se.cpp:413-452`
   reads `edge_cross_dxdy` and `areasvol` only. The operative reasons are missing edges and
   accumulation order.)
8. **The ring adds its own load imbalance.** Ring-1 size across CORE2 dist_64 ranks: min 70,
   median 128, max 177 (max/median 1.38). M9's L107 — a ring zone that differs per rank
   substitutes a new imbalance for the removed messages — applies here at that magnitude.

## Development Approach

- **Testing approach: gate-first.** Every gate below is pre-registered with its pass criterion
  *before* the run that decides it (house rule; M9/M11/M12 precedent). The project's "tests" are
  `ctest` plus the byte/fidelity/screen gate ladder, not unit tests — there is no unit-test
  harness in this codebase and this plan does not invent one.
- Complete each task fully, with its gate green, before starting the next.
- **Never guess a number that can be counted** — the census tooling exists now; extend it rather
  than estimating.
- Binaries → `/work` + sha only, never committed. `BIN=` pinned in every job (multi-srun re-execs).
- Cheap gates get `-t 00:06:00`-class walltimes so they look cheap to the scheduler.

- No atomics in the SE path — gather forms only (SASS-audited in M12; re-audited in Task 5).

🔴 **Why W1 was retired** (user decision 2026-08-14, on the measured evidence in the FINDING
below): the certified SE module computes ~0.55 % of elements on more than one rank and never
reconciles them, so the baseline's η carries *which rank owns the node*. No local recomputation
can reproduce that, and demanding it would be demanding reproduction of a partition artefact. W1′
states what is actually true and provable, and the residual is quantified rather than asserted.

**Why W2 is a selfcheck and not an A/B.** M12's own G2 established that the CUDA coupled state is
*not* run-to-run byte-reproducible: the 3-D model's certified D22 atomic scatters feed R̄, so two
identical CUDA runs already differ. A CUDA A/B byte gate is therefore impossible, and a
"climate-close" budget cannot distinguish an exact transformation from a broken one. The EVPWIDE
selfcheck — compute the ring locally *and* exchange, in the same run, then diff — is immune to
that nondeterminism and is decisive about the one thing that can silently break here: CSR
accumulation order.

🔴 **The selfcheck must stash BEFORE the exchange.** The η exchange has *replace* semantics: it
overwrites exactly the ring-1 slots the local kernel just wrote. Diffing after it would compare
the owner's value with itself and report a guaranteed `0.0` — a green gate over a broken
transformation. The comparator therefore copies the locally computed ring-1 η into a scratch
`fesom::Field` first, then diffs after the exchange (`fesom_evpwide_subcycle_exchange`'s
"max|refresh − local|", `fesom_ice_evpwide.h:80`, is the working precedent). This module has
already been bitten by the general form of this: see the "the CORE2 smoke died all-NaN under a
'0.000 PASS' banner" note at `fesom_ssh_se.cpp:1022-1025`.

**Deviation from the M12 GO decision, recorded.** `docs/plans/20260813-m12-split-explicit.md:467`
names a *solo subcycle harness* as the wide-halo prerequisite (it would also have closed G2's
CUDA module-isolation gate). This plan does not build it: the in-run selfcheck (W2) answers the
same question — is the module's device arithmetic reproducible under the transformation — without
a second driver to maintain, and it answers it inside the real coupled run rather than a harness.
G2's module-isolation item stays open on the M12 side.

exchange count. If they disagree, (b) wins — it is the direct measurement.

**The mechanism.** `myDim_elem2D` is not a partition: **1341 of 244659 elements (0.55 %) at CORE2
dist_8 are claimed by more than one rank** (1340 by two, 1 by three — measured from the partition
files). Each claimant computes them, and no exchange reconciles them (rlist covers only
`[myDim, myDim+eDim+eXDim)`). With the **two-term viscosity V[Ūᵐ]−V[Ūⁿ]** those redundant
computations diverge from the first step at which the anchor Ūⁿ is nonzero — step 2, since the
cold start makes Ūⁿ ≡ 0 at step 1. The certified path hides this completely: η is exchanged, so
the node owner's copy wins everywhere. The rung recomputes η from ITS OWN copies, so it reproduces
a different — equally valid — member of the family.

property of the SE module, not a defect of the rung.** The rung is exact whenever the model's own
Ū is rank-consistent: proven for all of step 1 and for every substep of a `VISC=0` run.

## Technical Details

### A. The substep, before and after

Ranges are as the kernels write them: `se_ab3` indexes **components** (`2*Ne`), the others index
entities.

```
today (2 exchanges/substep):
  k1 se_ab3   [0, 2*(myDim_e+eDim_e))  Uab3 = AB3(U0,U1,U2), mean += Uab3/M
  k2 se_eta   [0, myDim_n)             eta_new = eta + (tau/M)(div(Uab3) - wf)
  XCHG eta    NOD2D            <-- deleted by this plan
  k3 se_ubt   [0, myDim_e)             U_new = U + (tau/M)(-f e_z x Uab3 - g H grad eta^AM4 + F + visc)
  XCHG Ubt    ELEM2D           <-- becomes ELEM2D_FULL

K=1 rung (1 exchange/substep):
  k1 se_ab3   [0, 2*(myDim_e+eDim_e+eXDim_e))
  k2 se_eta   [0, myDim_n+eDim_n)      ring-1 rows come from the owner's CSR, owner order
  k3 se_ubt   [0, myDim_e)             unchanged
  XCHG Ubt    ELEM2D_FULL              same partners as before, ~2.2x the entities each
```

### B. Why it is bitwise, not merely close

η on a ring-1 node is computed from (i) the owner's CSR row, shipped, in the owner's accumulation
order; (ii) `Uab3` at the row's elements, produced by the same `se_ab3` kernel from Ū history that
the exchange delivered bit-for-bit; (iii) `water_flux` and `ulevels`, both already halo-valid
(`fesom_bulk.cpp:731`, `fesom_ice_coupling.cpp:303`). Same inputs, same order, same compiled
kernel ⇒ same bits, on Serial and on CUDA alike. Nothing owned changes, so the whole trajectory is
unchanged.

### D. The extended-mesh contract (design of record; **not built by this plan**)

*The single rule:* extended entities are appended **in BFS ring order**, so "everything within
ring r" is the contiguous range `[0, N_r)`. A consumer then expresses rim shrink as a
`RangePolicy` upper bound — no indirection list, no ghost kernel, no extra launch (L109 by
construction; M9's LEAN writing beat its separate-kernel twin by ×1.8–5 in ice cost for exactly
this reason).

- **Index space.** Nodes: `[0,myDim)` owned, `[myDim,myDim+eDim)` ring 1, rings 2..K appended at
  `[N, N+next)`. Elements: rings 0–2 are today's `myDim | eDim | eXDim` layout — already
  contiguous, already ring-ordered (measured); deeper rings append.
- **What is shipped as owner bytes, never recomputed:** `elem_nodes` as local ids (today `-1` in
  the outer eXDim ring, `fesom_mesh.cpp:1214`), `gradient_sca`, `elem_area`, metric factor,
  coriolis, H0e/depth, `ulevels`/`nlevels`, and per-node operator rows in owner order. Rule: any
  quantity produced by a mesh-geometry loop is shipped (EVPWIDE v3).
- **Build path.** BFS at scatter time while the global arrays and `node_g2l`/`elem_g2l` are alive
  (`fesom_evpwide_mesh_hook` precedent), collective, K a build-time parameter, memory O(K·perimeter).
- **Service.** `fesom_halo_field_wide(f, kind, nl, nc, K, p)` filling rings 1..K, plus per-ring
  lists so a consumer may request fewer rings than were built. At K=1 it degenerates to
  `com_nod2D`/`com_elem2D_full` — which is precisely why the first rung needs none of it.
  ⚠️ The signature is **illustrative**: it was chosen with zero consumers built, and the second
  customer gets to change it.
- **Two customers, one shape.** SE takes ring values + operator rows + a window scheduler (rim
  shrink = one ring per substep). Higher-order advection takes ring values + geometry + vertex
  maps, once per step, no scheduler. Shaping the API around "values *and* computability on rings"
  rather than around SE windows is what makes the second customer cheap.
- **Explicit non-goal:** the certified ice EVPWIDE does not migrate onto this layer.

### E. Deep-K sizing, if Task 8 says go

K substeps need K rings (§Context 3). Per window the refresh must restore 3 Ū levels and 3 η
levels on rings 1..K (AB3/AM4 history), so bytes per window ≈ K·(6·ring_elems + 3·ring_nodes)
against 2K messages saved. At CORE2 dist_64, K=8: ~19 k doubles per window versus 2.7 k today over
the same 8 substeps — 7× the bytes for 1/16 of the messages. That trade is only sane if Gate 0
says the wait is latency, which is the whole point of running Gate 0 first.
