# M5.12 — GPU throughput optimisation (stacked tactical levers)

## Overview

Implement a stacked set of tactical optimisations to reduce launch-density and
launch-overhead cost on the Kokkos GPU build. Each sub-milestone is independently
shippable behind its own validation gate. The plan is evidence-driven: every lever
and its expected payoff comes from M5.11 measurements, the OMEGA paper, or the
fence audit — not guesswork.

- **Problem it solves**: After M5.9-pin the GPU build sits at 0.478 s/step on
  CORE2 dist_8 (7× slower than CPU per node) and 6.005 s/step on dars n4
  (4.1× slower per node — see `docs/SCALING_DARS.md`). M5.11 profiling
  (`docs/PROFILE_M59.md`) identified the wall as **launch density**: 2450+
  launches/step at dist_8, top kernel only 1.51% of step, top 12 kernels
  combined &lt; 8%, per-call costs 13–30 µs near the bare CUDA launch-overhead
  floor. PCIe (1 GB/step) is no longer dominant; memory-coalescing was
  ruled out by M5.10b/Lever C (1.3% gain on FCT). The next move must be
  launch-count reduction + per-launch-overhead reduction.

- **Realistic target**:
  - CORE2 dist_8: 0.478 → ~0.41 s/step (**10–15%**) without M5.12h;
    → ~0.36 s/step (**20–25%**) with M5.12h.
  - dars n4: 6.005 → ~5.0–5.4 s/step (similar fractional gain).
  - **Per-watt parity on Levante A100 is not realistically reachable** and is
    not a goal of this plan. OMEGA reports 1.2× per-watt on A100 — that's the
    published ceiling for shallow-water full GPU code; our full-physics target
    is meaningful improvement, not parity.

- **Discarded levers** (kept for record):
  - **mEVP / aEVP** (algorithmic subcycle reduction): user explicitly rejected —
    production uses 120 subcycles even with mEVP, for sea-ice quality.
  - **Mixed precision (FP32)**: high validation cost (per-kernel M3.2 re-verify),
    deferred indefinitely.
  - **M5.12a halo fusion** (original M512_PLAN.md): superseded by **M5.12g halo
    aggregation** (the OMEGA pattern).
  - **M5.12c CG further fusion**: M5.2 already fused the big one, &lt; 0.5%
    remaining.
  - **Kokkos::Graph as priority #1 (NOT as a lever altogether)**: ruled out
    as the FIRST priority by OMEGA evidence (they get 6.1× on A100 with no
    graphs). Still in scope as M5.12e (the EVP-specific application is novel
    and the only known answer for EVP's 120-subcycle launch density).

## Development Approach

This is a stacked-tactical-optimisation milestone of a scientific-model port.
The generic "unit-test-per-function/TDD" model does not fit. "Tests" here are
**validation gates** provided by the existing per-kernel-verify + SYNCCHECK +
GPU-fidelity-gate infrastructure.

- **Validation gates** (the "tests") — apply per sub-milestone:
  1. **Per-kernel verify on Serial**: `FESOM_KK_VERIFY=<key>` `max|Δ|==0` for
     every key the sub-milestone touches. This is the bedrock — Serial bit-identity
     means the change is mathematically equivalent.
  2. **SYNCCHECK clean**: `build-synccheck` run produces no assertions.
  3. **GPU fidelity gate**: `scripts/gpu_fidelity_gate.sh` PASSES at the
     established noise floor (currently 1.0e-2 on h_ice, 6e-4 on T) against
     the 2026-05-28 `today_serial` oracle. Refresh oracle with `--fresh-oracle`
     after `fesom_step.cpp` changes (L51).
  4. **Same-day perf baseline** on CORE2 dist_8: build the prior commit on the
     same hardware before measuring (L40). Compare s/step apples-to-apples.
  5. **M3.2 climate spot-check** (1-yr CUDA): required ONLY when per-kernel
     verify is NOT bit-identical on Serial OR numerics could plausibly shift.
     M5.12f and M5.12d should be bit-identical on Serial (skip M3.2);
     M5.12g, M5.12b, M5.12e, M5.12h all need it.

- **Backward-compat hygiene**: no API changes to public headers without a
  call-site update in the same commit. No comments referencing "M5.12 plan"
  in the code (the PR description carries that context).

- **Per-sub-milestone commit + tag**: each M5.12x lands as its own commit on
  the working branch. Tag the final commit as `m5.12-stack-{N}` where N is
  the highest sub-milestone completed (so we can bisect performance later).

- **Lesson capture**: after each sub-milestone closes, append to
  `docs/KOKKOS_PORTING_LESSONS.md` as L53, L54, ... — keep the lever-pattern
  + the surprise (per existing convention: L47 M5.1a, L48 M5.4-5.5, L49
  M5.6-5.8, L50 M5.9-pin, L51 stale-oracle, L52 launch-density).

- **Plan tracking during implementation**:
  - mark `[x]` immediately when a step completes
  - add ➕ for newly discovered tasks
  - ⚠️ for blockers
  - update this plan if scope changes

## Testing Strategy

This plan's "tests" are the validation gates above. No new unit tests are
written; the existing per-kernel verify infrastructure IS the unit-test layer
for kernel changes (it compares the new kernel's output to the C twin / Serial
oracle to bit-identity on Serial).

- **Per-kernel verify**: each sub-milestone declares which keys it touches and
  runs the verify against `build-serial` after the change.
- **Climate-close gate**: GPU fidelity gate against the fresh oracle after
  any sub-milestone that could shift numerics on CUDA.
- **Perf measurement**: same-day baseline before/after — see L40.
- **No project-level test command exists**; the validation gates are the
  test suite.

dist_8 (1× bvfreq + 9× blmc-3-slab). The 9 blmc calls run the same 9-sweep

### M5.12e — Kokkos::Graph for EVP subcycle (the novel one)

**Files:**
- Create: `src/fesom_ice_evp_graph.{hpp,cpp}`

  `#ifdef KOKKOS_ENABLE_CUDA` with env override `FESOM_EVP_GRAPH=0` to
  force the non-graph path for A/B comparison)

Capture one EVP subcycle's kernels as a `Kokkos::Graph` and replay 120× per
step. Halo MPI between subcycles forces a graph boundary — can't capture
into the graph. Pattern: graph captures all 3 team-fused kernels from M5.12b
(or all 7 if M5.12b not yet landed) of one subcycle including the post-vel_update
halo pack; replay 120 times with per-subcycle halo MPI between graph submits.

Per Ekelund et al. (arXiv 2501.09398), iteration-batch unrolling with N nodes
in a graph gets 1.2–1.5× on A100 for similar small-kernel patterns. 120
iterations × 3 fused kernels = 360 nodes per batch — within Ekelund's measured
sweet spot.

  `build-serial`).

  plausibly shift.
- Same-day perf baseline = 2 builds + 2 short timing runs ~30 min.

### Stacked-commit hygiene

Each sub-milestone is one commit. Don't combine. Tag the final commit
`m5.12-stack` so `git bisect` works for the next session if a perf
regression appears.

Sub-milestones are mostly INDEPENDENT in terms of touched files:
- M5.12f: `fesom_ssh.cpp` only
- M5.12d: `fesom_kpp.cpp` (+ smoother file)

sub-milestone fails the gate and needs investigation, the next one can
